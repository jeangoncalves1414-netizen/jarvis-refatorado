## Dependency notes

- The `.env` cleanup and route-resolution tests in Plan 001 must land before the UI is changed; otherwise the UI can report a provider that the backend silently replaces.
- Plan 002 must precede every interface de rede, celular, Raspberry Pi ou ação autônoma: uma UI de confirmação não é uma fronteira de segurança.
- Plan 003 consumes the identity and authorization primitives from Plan 002; Plan 004 only displays immutable action records created by Plan 003.
- Plan 005 must consume Action Kernel policies rather than inventing a second way to auto-execute a task.
- Plan 006 establishes isolated tests before Plan 007 moves high-churn modules.

## Findings considered and rejected

- Replacing all providers with a single service: rejected for now. The project intentionally supports Gemini, Groq, Oxyy, Fish, Edge and Google; the problem is route clarity and truthful status, not provider count.
- Removing Oxyy's per-capability model catalog: rejected. It is useful for image/video/embeddings, but it must be presented as a model choice inside an explicit capability route rather than as another active chat provider.
- Speaker diarization, continuous facial recognition and room hardware: deferred. They require the authentication, consent, event/audit and reliability foundations in Plans 002–005; adding them first would make the assistant less trustworthy.
