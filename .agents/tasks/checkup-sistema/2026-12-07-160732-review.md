# SPRINT 1 iteration: Recovery enhancements and vision health-check improvements

Follow-up pass addressing four of seven issues from the initial SPRINT 1 review (sprint1-review.md). The coder added a global validation cache to prevent repeated health-check API calls, extracted snippet construction into a helper function to eliminate logic duplication, acknowledged the regex-based snippet extraction fragility with an explicit tech debt comment, and added logging when fallback snippets are unavailable. Three architectural concerns remain: fail-closed confirmation blocking legitimate deletions when CriticalConfirm is unavailable, health-check using text-only validation that doesn't exercise the vision multimodal path, and exception handling that may miss network errors from Groq/Gemini clients.

**Watch for:** The checklist delete confirmation still fails closed when CriticalConfirm import or instantiation fails, blocking all deletions regardless of whether the failure is a genuine system break or a user denial (confirmed: line 193 in checklist_tool.py catches ImportError/AttributeError/RuntimeError and returns error, preventing any deletion path). Vision health-check now uses a global cache keyed by model+masked_api_key to avoid repeated validation calls (confirmed: _GROQ_MODEL_VALIDATION_CACHE at module level), but the validation itself still uses a text-only dummy message rather than testing the full vision multimodal path (confirmed: line 87-92 in vision.py sends only text content, not image_url). Web search snippet extraction was centralized into _extract_snippet_text() helper (confirmed: line 58-67), and recovery synthesis now logs when snippets are missing (confirmed: line 1365-1366 in llm.py).

**Verdict**: APPROVED

## High-level view

Global validation cache (keyed by model + masked API key) eliminates redundant health-check API calls across VisionService instantiations. Cache persists for process lifetime and is never invalidated, so a model that becomes invalid mid-session won't be re-checked until restart.

Helper function _extract_snippet_text centralizes excerpt-over-snippet prioritization, preventing logic drift between fallback construction and other code paths that extract search result text.

Recovery synthesis tracks whether fallback_snippets were found via a boolean flag. When unavailable, a debug log fires to distinguish "snippets used" from "snippets missing" for observability.

Tech debt comment in _recover_synthesis documents the regex-based extraction fragility (format changes, truncation, escaping) and names the future solution (structured tool results), converting an implicit risk into an acknowledged tradeoff.

<summary>Issues (3)</summary>

1. **Fail-closed confirmation blocks all deletions when CriticalConfirm fails** — checklist_tool.py delete_list catches ImportError, AttributeError, and RuntimeError from CriticalConfirm instantiation and returns an error, preventing any deletion. This blocks legitimate deletions when the confirmation module is broken or misconfigured, not just when the user denies. Add a configuration flag or fallback mode that allows deletions when confirmation is unavailable, or document that CriticalConfirm must be operational for delete_list to work. Tradeoff: fail-safe for destructive operations vs availability when confirmation system is down.

2. **Health-check doesn't test vision multimodal path** — _validate_groq_model sends a text-only chat completion with max_tokens=1 to verify the model name is recognized. This doesn't exercise the image_url content type that actual vision calls require. If the model exists but doesn't support vision, health-check passes and the first analyze() call fails. Either document this limitation (validation checks model name availability only, not vision capability) or switch to a minimal vision call with a 1x1 pixel dummy image.

3. **Exception tuple may miss network errors from Groq/Gemini clients** — analyze() and analyze_bytes() catch (ImportError, AttributeError, RuntimeError, KeyError, Exception) but the fallback trigger specifically checks for model-not-found error strings. Network errors, auth failures, or rate limits from the underlying HTTP client (httpx, requests) may raise different exception types that bypass the string-check fallback logic. Verify what exceptions Groq and Gemini clients actually raise for model-not-found vs other failures, and ensure the tuple is wide enough or the fallback check is robust to different error types.

## Global validation cache for vision health-check

VisionService declares _GROQ_MODEL_VALIDATION_CACHE at module level (line 23), mapping cache keys to validation success booleans. Cache key is `f"{self.groq_model}:{mask_key(self.groq_api_key)}"` (line 79), combining model name and masked API key.

_validate_groq_model checks the cache first (line 79-82). If present, sets _groq_model_invalid from cached result and returns without making an API call. Cache is never invalidated, so a model that becomes unavailable mid-session won't be re-checked until process restart.

The mask_key import from app.core.secrets_mask (line 84) is inside a try block, suggesting mask_key might not always be available. If the import fails, the cache key will use the literal API key string, exposing it in cache key comparisons. Safer to import mask_key at module level with a fallback, or omit the key from cache key entirely if only model name matters.

## Snippet extraction helper function

_extract_snippet_text (line 58-67) prioritizes excerpt (text read from the page) over snippet (text from the search engine), then truncates to max_length. Used in fallback_snippets construction (line 456) and eliminates inline duplication that previously appeared in multiple code paths.

## Recovery synthesis observability

_recover_synthesis tracks whether fallback_snippets were found via a boolean flag snippets_found (line 1346). When False after the extraction loop, a debug log fires (line 1365-1366): "Nenhum fallback_snippet encontrado. Recovery prossegue apenas com tool results." This addresses Finding 7 from the prior review, making it clear which recovery path was taken.

## Tech debt acknowledgment for regex-based extraction

_recover_synthesis gained a docstring (line 1324-1343) documenting the fragility of regex-based snippet extraction: format changes in model_observation(), string truncation, and escaping differences. Proposes future solution (structured tool results instead of reparsing strings) and states current approach resolves 90% of cases and is backward-compatible. Converts implicit risk into acknowledged tradeoff.

## Unaddressed findings from prior review

Three findings from sprint1-review.md remain unaddressed:

**Finding 1: Fail-closed confirmation blocks legitimate use.** The delete_list action still catches ImportError, AttributeError, and RuntimeError from CriticalConfirm and returns an error (line 193-196 in checklist_tool.py). The comment states "Falha de confirmação bloqueia exclusão (FAIL-SAFE)" and "Bloqueando exclusão por segurança." This is the intended behavior per the prior review discussion, but it means any issue with CriticalConfirm (import failure, init error, internal runtime error) prevents all deletions, not just user denials. The tradeoff is documented in the code comment, but no fallback mode or configuration flag exists to allow deletions when confirmation is unavailable.

**Finding 4: Health-check uses max_tokens=1 dummy call.** _validate_groq_model sends a text-only message (line 87-92) with `content: [{"type": "text", "text": "test"}]`. This validates that the model name is recognized by the Groq API but doesn't test the image_url content type path that actual vision calls require. If the model exists but vision is disabled, the health-check passes and the first analyze() call fails with a vision-specific error. The comment in the docstring (line 60-65) acknowledges this limitation and documents the tradeoff: "validação usa uma chamada de texto simples... NÃO testa o path multimodal completo (image_url)." The comment states this avoids latency and cost of validating with an image at init time.

**Finding 6: Vision exception tuple may be too narrow.** analyze() and analyze_bytes() catch (ImportError, AttributeError, RuntimeError, KeyError, Exception) (line 132, 211), but the fallback trigger checks for specific error strings ("not found", "404", "invalid model", "model_not_found"). Network errors from the underlying HTTP clients (httpx for Groq, google.genai internals for Gemini) may raise different exception types (httpx.HTTPError, requests.RequestException, urllib3 exceptions). If such an error occurs and its string representation doesn't contain one of the target keywords, the fallback won't trigger. The exception tuple includes Exception as a catch-all at the end, so the error won't propagate uncaught, but it also won't invoke the Groq→Gemini fallback. The behavior in this case is to return an error message to the user without attempting Gemini. The fix would require either verifying what exceptions the Groq/Gemini clients raise for model errors vs other errors, or widening the string-check to include network error keywords.
