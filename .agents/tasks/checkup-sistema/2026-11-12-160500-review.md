# SPRINT 1: Confirmação de exclusão, fallback de busca web, e visão Groq→Gemini

Três correções defensivas foram implementadas para lidar com operações destrutivas, falhas de API, e obsolescência de modelos. A correção de checklist adiciona uma camada de confirmação antes de exclusões irreversíveis, a correção de busca web preserva snippets brutos quando a síntese falha por rate limit, e a correção de visão implementa fallback automático Groq→Gemini quando o modelo qwen configurado retorna 404.

**Watch for:** Silent exception suppression na confirmação de checklist (confirmed); ausência de validação de modelo na inicialização do VisionService (confirmed); fallback_snippets não usado por recovery downstream (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

A confirmação de exclusão de checklist instancia `CriticalConfirm` e chama `request()`, mas suprime silenciosamente exceções de import ou runtime — se o módulo de confirmação falhar, a exclusão prossegue sem confirmação, contrariando o propósito da correção.

Os snippets compactos construídos pela web_search tool (title[:100], snippet[:400], limitados a 5 resultados) estão presentes no `data` do ToolResult e expostos ao modelo via `model_observation()` no base.py, mas nenhum código downstream (`_recover_synthesis` ou equivalente) foi modificado para consumir esses snippets em caso de falha — a correção preserva os dados, mas não implementa a recuperação.

A lógica de fallback Groq→Gemini em `VisionService.analyze()` e `analyze_bytes()` usa detecção de keywords ("not found", "404", "invalid model") para identificar erros de modelo obsoleto. A correção é reativa: o erro acontece em produção, o fallback dispara, e o `print()` registra o evento, mas a inicialização do serviço não valida se o modelo Groq configurado existe antes de tentar usá-lo.

<details>
<summary>Issues (5)</summary>

1. **Silent confirmation failure** — Se `CriticalConfirm` não puder ser importado ou `request()` lançar exceção, o `except Exception: pass` suprime o erro e a exclusão prossegue sem confirmação. Adicione logging ou retorne erro quando a confirmação for solicitada mas falhar.

2. **Fallback snippets não consumidos** — Os snippets estão presentes no ToolResult.data, mas `_recover_synthesis` (ou o código que lida com rate limit na síntese) não foi modificado para consumi-los. Implemente a lógica de recovery que monta a resposta a partir de `fallback_snippets` quando a síntese falhar.

3. **Validação de modelo ausente na inicialização** — VisionService aceita qualquer string em `GROQ_VISION_MODEL` sem verificar se o modelo existe. Adicione um health-check na inicialização que valida o modelo Groq ou marque-o como inválido para fallback imediato, evitando latência de erro no primeiro request.

4. **Fallback assume presença de chave Gemini** — Se a configuração usa apenas Groq (sem chave Gemini configurada), o fallback falha com mensagem de erro mas não há mecanismo para prevenir essa situação na inicialização. Valide que pelo menos uma das chaves está configurada, ou documente que Gemini é obrigatório como fallback.

5. **Exceções genéricas capturadas** — O bloco `except Exception` no checklist e no fallback de visão captura tudo, incluindo KeyboardInterrupt e SystemExit em Python <3.8. Use `except (ImportError, RuntimeError)` ou outra lista específica de exceções esperadas.

## Confirmação de exclusão de checklist

A correção injeta um bloco de confirmação antes de `checklist_store.delete_list()`. O código monta uma mensagem descritiva com o nome da lista e a contagem de itens, instancia `CriticalConfirm`, e chama `request(tool="checklist_tool", detail=...)`. Se `approved` é falso, retorna `{"ok": False, "error": "Exclusão cancelada pelo usuário."}` sem tocar o store.

O problema é o `except Exception: pass` que envolve todo o bloco de confirmação:

```python
try:
    from app.core.critical_confirm import CriticalConfirm
    critical = CriticalConfirm()
    approved = critical.request(tool="checklist_tool", detail=detail)
    if not approved:
        return {"ok": False, "error": "Exclusão cancelada pelo usuário."}
except Exception:
    pass  # Se CriticalConfirm falhar, prossegue sem confirmação
```

Se `CriticalConfirm` não puder ser importado (módulo não existe, erro de importação), ou se `request()` lançar exceção (bug, configuração ausente), o código silenciosamente prossegue para `checklist_store.delete_list(target["id"])`. O comportamento esperado era bloquear a exclusão até obter confirmação; o comportamento real é fail-open.

A correção deveria ou falhar explicitamente quando a confirmação não puder ser solicitada (retornar erro), ou ao menos logar o evento para auditoria. A mensagem de commit diz "confirmação antes de excluir", mas a implementação é "confirmação antes de excluir, a menos que a confirmação quebre".

## Fallback snippets na busca web

A correção constrói uma lista de até 5 resultados compactados logo após a chamada `_format_search_response()`:

```python
fallback_snippets = [
    {
        "title": r.get("title", "")[:100],
        "url": r.get("url", ""),
        "snippet": (r.get("excerpt") or r.get("snippet") or "")[:400],
        "source": r.get("source", ""),
    }
    for r in results[:5]
]
```

Esses snippets são incluídos em `ToolResult.data` e expostos ao modelo via `model_observation()`, mas o consumidor não existe. O objetivo declarado no ponto 8 era "guardar os snippets crus como fallback, para que o `_recover_synthesis` tenha material para montar a resposta" quando a síntese for cortada por rate limit. A correção preserva os snippets, mas `_recover_synthesis` (ou o código que lida com rate limit no turno de síntese) não foi modificado neste commit. Se a síntese falhar, o recovery atual não tem lógica para reconstruir a resposta a partir de `fallback_snippets`.

A correção é 50% implementada: os dados estão disponíveis, mas a recuperação ainda não acontece.

## Fallback Groq→Gemini em VisionService

A correção adiciona dois blocos de fallback idênticos em `analyze()` e `analyze_bytes()`. Quando uma exceção é lançada pela chamada Groq, o código verifica se a mensagem de erro contém keywords indicando modelo inexistente ("not found", "invalid model", "404", "model_not_found", "model not found"). Se sim, e se o provider ativo é "groq", tenta novamente usando Gemini Vision:

```python
if is_model_error and active_provider == "groq":
    print(f"[Vision] Modelo Groq '{self.groq_model}' inválido ou obsoleto. Fallback para Gemini Vision.")
    try:
        # ... código Gemini ...
        ok = True
    except Exception as fallback_error:
        ok = False
        reply = f"Fallback para Gemini Vision também falhou: {fallback_error}. Erro Groq original: {e}"
```

A estratégia é reativa: o erro acontece em runtime, o fallback dispara. Isso atende o requisito do ponto 2 ("fallback para Gemini Vision automaticamente"), mas não atende "health-check na inicialização". A correção falha rápido no primeiro request, mas impõe latência de rede + erro + retry na primeira tentativa de visão.

A detecção de erro por keywords é frágil mas razoável. O `print()` para stdout deveria usar logger em produção.

A correção assume que `self.api_key` contém uma chave Gemini válida. Se a configuração usa apenas Groq (sem chave Gemini), o fallback falha com "Fallback Gemini solicitado mas chave de API não configurada". Não há validação na inicialização que garanta pelo menos uma das chaves está presente.
